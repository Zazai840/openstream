# macOS hotkey event research

Context: [Which macOS keys can reliably drive the push-to-talk shortcut?](https://github.com/Nabzx/openstream/issues/199) is part of [Map: verify one configurable push-to-talk shortcut](https://github.com/Nabzx/openstream/issues/198).

## Verified facts

### Event path and function keys

- The native helper creates a session event tap with `.listenOnly` and asks for only `keyDown` and `keyUp`. A listen-only tap receives events without modifying or diverting them. [`native/hotkey-helper/Sources/hotkey-helper/main.swift`](../../native/hotkey-helper/Sources/hotkey-helper/main.swift), [CGEventTapLocation.cgSessionEventTap](https://developer.apple.com/documentation/coregraphics/cgeventtaplocation/cgsessioneventtap), [CGEventTapOptions](https://developer.apple.com/documentation/coregraphics/cgeventtapoptions), [CGEventTapCallback](https://developer.apple.com/documentation/coregraphics/cgeventtapcallback)
- Apple defines virtual keycodes for F1 through F19. The values in the Apple SDK `Events.h` header are: `F1=0x7A`, `F2=0x78`, `F3=0x63`, `F4=0x76`, `F5=0x60`, `F6=0x61`, `F7=0x62`, `F8=0x64`, `F9=0x65`, `F10=0x6D`, `F11=0x67`, `F12=0x6F`, `F13=0x69`, `F14=0x6B`, `F15=0x71`, `F16=0x6A`, `F17=0x40`, `F18=0x4F`, and `F19=0x50`. [`Events.h` in the Apple SDK mirror](https://github.com/phracker/MacOSX-SDKs/blob/master/MacOSX10.6.sdk/System/Library/Frameworks/Carbon.framework/Versions/A/Frameworks/HIToolbox.framework/Versions/A/Headers/Events.h)
- Those declarations do not guarantee a physical keyboard will emit a normal pair. Apple says that volume, brightness, and CD-eject keys on some keyboards do not generate `keyDown` or `keyUp` events. Apple also documents that the top row of Apple keyboards controls system features by default, and that Fn/Globe or the "Use F1, F2, etc. keys as standard function keys" setting changes that behavior. [CGEventSource.counterForEventType](https://developer.apple.com/documentation/coregraphics/cgeventsource/counterforeventtype(_:eventtype:)), [How to use the function keys on your Mac](https://support.apple.com/en-us/102439)
- If a keyboard does emit a normal F-key event, its virtual keycode is available from `keyboardEventKeycode`, so this tap can match it. That is a conditional capability, not a reliable all-keyboards product promise. [CGEventField.keyboardEventKeycode](https://developer.apple.com/documentation/coregraphics/cgeventfield/keyboardeventkeycode), [`main.swift`](../../native/hotkey-helper/Sources/hotkey-helper/main.swift)

### Modifiers and Fn

- `flagsChanged` is the event type for a modifier or status-key change. Apple explicitly says modifier keys produce `flagsChanged`, rather than `keyDown`, on both press and release. The current tap does not request `flagsChanged`, and the callback ignores it, so pressing only Control, Option, Shift, or Command cannot start or stop OpenStream. [`main.swift`](../../native/hotkey-helper/Sources/hotkey-helper/main.swift), [CGEventType.flagsChanged](https://developer.apple.com/documentation/coregraphics/cgeventtype/flagschanged), [CGEventSource.counterForEventType](https://developer.apple.com/documentation/coregraphics/cgeventsource/counterforeventtype(_:eventtype:)), [Handling Key Events](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/HandlingKeyEvents/HandlingKeyEvents.html)
- macOS represents Fn with `CGEventFlags.maskSecondaryFn`, documented as the Fn key being down for a keyboard, mouse, or flags-changed event. The older Events header also names `kVK_Function` as virtual keycode `0x3F`. The public representation is therefore a flag, not evidence of a universally available standalone `keyDown`/`keyUp` trigger. [maskSecondaryFn](https://developer.apple.com/documentation/coregraphics/cgeventflags/masksecondaryfn), [CGEventFlags](https://developer.apple.com/documentation/coregraphics/cgeventflags), [`Events.h`](https://github.com/phracker/MacOSX-SDKs/blob/master/MacOSX10.6.sdk/System/Library/Frameworks/Carbon.framework/Versions/A/Frameworks/HIToolbox.framework/Versions/A/Headers/Events.h)
- The four ordinary modifier classes have separate event-flag masks: Command, Option, Control, and Shift. The current helper can distinguish those classes, but its stored representation and comparison do not distinguish left from right. [`main.swift`](../../native/hotkey-helper/Sources/hotkey-helper/main.swift), [CGEventFlags](https://developer.apple.com/documentation/coregraphics/cgeventflags)

### Layout and system boundaries

- A `CGKeyCode` identifies a hardware key position, not a character chosen by the active layout. Apple describes the codes as hardware-independent, while the SDK header warns that ANSI names describe US keyboard positions and that another layout can put the `A` label on a different physical key. [`Events.h`](https://github.com/phracker/MacOSX-SDKs/blob/master/MacOSX10.6.sdk/System/Library/Frameworks/Carbon.framework/Versions/A/Frameworks/HIToolbox.framework/Versions/A/Headers/Events.h), [CGKeyCode](https://developer.apple.com/documentation/coregraphics/cgkeycode)
- Secure Event Input can stop keyboard-intercept processes, including CGEvent-tap processes, from receiving keyboard events while it is enabled. This is a macOS boundary outside the helper's control. [TN2150: Using Secure Event Input Fairly](https://developer.apple.com/library/archive/technotes/tn2150/_index.html)
- A listen-only tap leaves the shortcut in the normal event stream. A configured combination may therefore also invoke an application or system action. Apple lists examples of reserved function-key combinations such as Control-F1 and Control-F7. [CGEventTapOptions](https://developer.apple.com/documentation/coregraphics/cgeventtapoptions), [Accessibility keyboard shortcuts](https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/OSXAXKeyboardShortcuts.html)

## Implications for OpenStream

- The settings renderer currently accepts only the keys in `DOM_CODE_TO_MAC_KEYCODE`, which excludes F1-F19 and Fn. It listens for `keydown` and stores only the four DOM modifier booleans. A function key may be technically matchable by the native helper, but the current settings flow cannot configure one. [`src/hotkey/keycodeMap.ts`](../../src/hotkey/keycodeMap.ts), [`src/hotkey/captureHotkey.ts`](../../src/hotkey/captureHotkey.ts), [`src/HotkeySettings.tsx`](../../src/HotkeySettings.tsx)
- A modifier-only shortcut cannot work with the current helper. Supporting it would require observing `flagsChanged` and maintaining modifier state, and would also require a renderer capture path for that gesture. [`main.swift`](../../native/hotkey-helper/Sources/hotkey-helper/main.swift), [`src/HotkeySettings.tsx`](../../src/HotkeySettings.tsx)
- Exact comparison of the four selected masks is reasonable for deciding whether a base-key `keyDown` has exactly the configured ordinary modifiers. It is not a complete exact-gesture match: the helper deliberately ignores Fn and other flags, cannot tell left from right, and requires the same modifier masks on `keyUp`. If the user releases a required modifier before the base key, the matching `keyUp` is missed. [`main.swift`](../../native/hotkey-helper/Sources/hotkey-helper/main.swift)
- The safest current product promise is one non-modifier key plus one or more of Control, Option, Shift, and Command, subject to the key being an ordinary keyboard event and the combination not being reserved. F1-F12 should not be promised across Mac keyboard modes. F13-F19 can be conditionally supported on hardware that has them and emits ordinary events, but the repository has no cross-hardware evidence for a universal promise. [`src/hotkey/keycodeMap.ts`](../../src/hotkey/keycodeMap.ts), [`electron/hotkeyHelper.js`](../../electron/hotkeyHelper.js), [How to use the function keys on your Mac](https://support.apple.com/en-us/102439)
- Because the tap is listen-only, choosing a Command shortcut can have application side effects. The repository already records the observed consequence for an unmatched Command shortcut: AppKit may beep, and that beep can enter the recording. [`electron/hotkeyHelper.js`](../../electron/hotkeyHelper.js), [`docs/testing/hotkey-transcribe-manual-check.md`](../testing/hotkey-transcribe-manual-check.md)

## Unresolved questions

1. Apple documents the conditions but does not provide a per-model event matrix. A real Mac test must cover an Apple laptop with default top-row behavior, the standard-function-key setting, Fn+F1 through Fn+F12, an Apple external keyboard, and keyboards exposing F13-F19. [CGEventSource.counterForEventType](https://developer.apple.com/documentation/coregraphics/cgeventsource/counterforeventtype(_:eventtype:)), [How to use the function keys on your Mac](https://support.apple.com/en-us/102439)
2. The exact behavior of a standalone Fn press, including whether it supplies a stable flags-changed press/release pair on each supported keyboard, remains unverified here. The public API exposes the Fn flag, but no source found promises universal delivery. [maskSecondaryFn](https://developer.apple.com/documentation/coregraphics/cgeventflags/masksecondaryfn), [CGEventType.flagsChanged](https://developer.apple.com/documentation/coregraphics/cgeventtype/flagschanged)
3. The product needs a deliberate policy for left/right modifiers and release order. The current event format collapses both sides into one mask, and the current key-up matcher is order-sensitive. [`main.swift`](../../native/hotkey-helper/Sources/hotkey-helper/main.swift)
4. The exhaustive set of system-reserved shortcuts varies with macOS features, user settings, and applications. OpenStream should test candidate defaults on supported macOS versions rather than promise that any arbitrary combination is harmless. [Accessibility keyboard shortcuts](https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/OSXAXKeyboardShortcuts.html), [Mac keyboard shortcuts](https://support.apple.com/en-us/102650)
5. This note did not run a physical-keyboard experiment. The conclusions above are from Apple documentation, the SDK header, and the current repository code. Input Monitoring permission and Secure Event Input behavior still need a human check on target Macs. [`main.swift`](../../native/hotkey-helper/Sources/hotkey-helper/main.swift), [TN2150: Using Secure Event Input Fairly](https://developer.apple.com/library/archive/technotes/tn2150/_index.html)
